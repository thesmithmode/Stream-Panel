# Stream Panel

Личная серверная панель аналитики Twitch, DonationAlerts и YouTube для Руслана и Гульназ. Сбор работает на Linux VPS круглосуточно; браузер можно закрыть. Windows и Linux используются как клиенты браузера, установки приложения на компьютеры больше не нужны.

Один физический SQLite на сервере, отдельные таблицы, настройки интеграций и парольные сессии для каждого профиля. Объединение людей и донатов выполняется только внутри своего профиля. YouTube хранится отдельно от Twitch/DA: совпадающий ник не связывает людей между платформами автоматически.

Публичной регистрации нет. Доступ к API требует парольной сессии; изменения — также CSRF и точный Origin. Пароли хранятся как scrypt-хэши; cookie HttpOnly/Secure/SameSite=Lax. Перезапуск сервера сохраняет сессии, выход отзывает выбранную сессию. SQLite WAL и IMMEDIATE-транзакции защищают параллельные записи, конфликты ревизий возвращают 409.

## Запуск для разработки

Node.js 24.19.0, pnpm 11.25.0, Linux:

```sh
pnpm install --frozen-lockfile
pnpm build
export STREAM_PANEL_DATA_DIR=/absolute/private/directory
export STREAM_PANEL_PUBLIC_ORIGIN=http://127.0.0.1:47831
# Создать аккаунты через stdin, без паролей в argv/history или git.
# JSON: [{"profile":"ruslan","username":"...","displayName":"Руслан","password":"..."}, ...]
node scripts/provision-accounts.mjs < /path/to/private/accounts.json
pnpm start
```

Пароль не короче 14 символов. Второй profile — `gulnaz`. Приложение слушает только 127.0.0.1; публичный доступ — через HTTPS-прокси. В production HTTP запрещён. Нет дефолтных паролей и root-логина через панель.

## Интеграции

- Twitch: свой public OAuth client, Device Code; Client Secret не нужен. Chatters — наблюдения участников чата, а не доказательство просмотра видео.
- DonationAlerts: OAuth-приложение, redirect из «Интеграций» на публичный HTTPS URL. Пока UTC offset не подтверждён, время доната остаётся неизвестным.
- YouTube: Google OAuth web client, YouTube Data API v3 + YouTube Analytics API, read-only scopes. Каждый входит в свой Google/Brand Account. Redirect из «Интеграций»; отчёты за 28 дней обновляются раз в 6 часов. Активные эфиры проверяются раз в 1–5 минут, до двух чатов на профиль; соблюдается pollingIntervalMillis. Локальный бюджет — 4000 единиц/профиль/день по Pacific Time, сохраняется в БД. Внешнее использование того же Google проекта может исчерпать квоту раньше.

Google OAuth в Testing может ограничивать срок refresh-токенов; настройка проекта и живой эфир проверяются перед production. Исторический чат до подключения и скрытые зрители не восстанавливаются. Смена канала показывает только его данные.

## Развёртывание и автоматические обновления

Инструкция: [docs/ops/server.md](docs/ops/server.md). `main` и `dev` сохраняются. Quality gate проверяет Linux, TypeScript/Svelte, unit/integration/e2e, покрытие ≥95%, серверный bundle и откат деплоя. CI собирает серверный архив для Linux amd64 с привязкой к SHA коммита. Автодеплой VPS включается переменной `STREAM_PANEL_PRODUCTION_ENABLED=true` после проверки живого сервера. Старый desktop release v0.0.4 остаётся историческим.

Отдельные systemd-пользователи, каталоги, лимиты CPU/RAM, forced-command deploy key. При обновлении: maintenance → остановка службы → согласованный снимок → новая неизменяемая версия → healthcheck → включение сбора. Ошибка возвращает предыдущую версию, БД и настройки. Ротация сохраняет три версии и три снимка, затрагивая только каталоги Stream Panel.

Без покупки домена используется `stream-panel.<IP-с-дефисами>.sslip.io` и отдельный Caddy с автоматическим TLS. DNS/ACME и свободные 80/443 проверяются на выбранном сервере. Занятый порт означает остановку установки, существующий прокси не перезаписывается.

## Бэкапы

SQLite — единственный источник данных. Supabase используется только как закрытое Storage-хранилище шифрованных копий, синхронизация Postgres удалена. Копия содержит обе БД-профильные схемы, хэши аккаунтов и настройки подключений, шифруется AES-256-GCM после gzip. Ключ хранится отдельно; нужны отдельная сохранённая копия ключа и проверка восстановления.

Копии создаются каждые 24 часа и вручную (не чаще раза в 10 минут). Локально сохраняются как минимум семь последних точек; календарная политика добавляет точки за последние семь дней и три недельных окна в пределах 30 дней. Номинальный локальный бюджет — 2 GiB; семь последних точек имеют приоритет над бюджетом. Старые копии удаляются по политике хранения; последняя успешная точка не заменяется непроверенной.

Без настроенного Supabase работают локальные шифрованные копии. Payload свыше 1 MiB обрабатывается потоково в формате SPBK2; старые SPBK1 читаются по-прежнему. Payload и файл SPBK2 ограничены 64 GiB, метаданные — 1 MiB; это предел формата, а не обещание достаточного места на диске. Создание проверяет запас диска и целостность снимка. Скачивание и восстановление больших копий не загружают всю БД в память. Облачные копии до 48 MiB хранятся одним объектом, более крупные — проверенными частями по 16 MiB и манифестом. Отдельный облачный бюджет задаётся `STREAM_PANEL_CLOUD_BACKUP_BUDGET_BYTES` (в серверной точке входа по умолчанию 1 000 000 000 байт). При его превышении сохраняется локальная копия и отображается ошибка облака. Перед деплоем снимки находятся только в закрытом серверном каталоге.

```sh
node scripts/restore-backup.mjs /private/backup.spbk /private/backup-key /new/empty/directory
```

Восстановление проверяет integrity/FK и отзывает старые сессии. Службу остановить до переключения каталога данных. Ключ и service-role key никогда не передаются браузеру.

## Поддерживаемость и очередь запросов

HTTP-обработчики людей, стримов и донатов регистрируются отдельными модулями; схемы и проверки доступа остаются общими. RPC выводит тип ответа из операции; адаптеры интеграций зависят от узких структурных контрактов. Список людей имеет серверную пагинацию с фильтрацией ботов до разбиения на страницы.

Исторические отчёты разных фильтров сохраняют независимый прогресс: одновременно удерживаются не более четырёх задач, неактивные освобождаются через пять минут. При большем числе разных фильтров наименее недавно использованный расчёт может быть подготовлен повторно. SQLite-записи обоих профилей выполняются общим worker. Защищённый status содержит число ожидающих запросов и максимальное время ожидания/выполнения по операциям; ожидание включает IPC. Неответивший worker останавливается после 60 секунд ожидания RPC (для копирования БД — не менее 10 минут), затем используется существующий перезапуск службы. Результат прерванной записи может быть неопределённым, поэтому клиент не повторяет мутации автоматически.

# TDD и автоматическая проверка

Требование владельца от 2026-10-06: [user-requirements.md](user-requirements.md). Проверки относятся к согласованной аналитической v1 из [PRD](prd.md); они не расширяют продукт до полного набора виджетов Stream Tools.

## Рабочий цикл

1. Выбрать один контракт из PRD/спецификации: переключение профиля, событие, результат, отказ и восстановление.
2. Добавить тест и выполнить его на текущем коде. Зафиксировать конкретное падение: ошибка результата, а не только отсутствие импорта.
3. Внести минимальное исправление, получить зелёный тест, выполнить связанные регрессии.
4. Рефакторить после зелёного результата; сделать небольшой коммит завершённой задачи. Перед публикацией проверить весь `pnpm check`.

В PR/коммите описывается поведение и проверка. Изменения миграций дополнительно проверяются на старой базе; ошибки сети/диска — с восстановлением очереди и сохранностью данных. Для новой интеграции отдельно отмечается, что подтверждено fixture, а что реальным сервисом.

## Запуск

Нужны версии Node/pnpm из README. После `pnpm install --frozen-lockfile` установить Chromium: `pnpm exec playwright install chromium`. На Linux чистый runner также требует системные библиотеки: `pnpm exec playwright install --with-deps chromium`; это команда CI. В ограниченной среде можно указать существующий совместимый Chromium через `STREAM_PANEL_TEST_CHROMIUM`.

| Команда                 | Проверка                                                                                                          |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `pnpm test:unit`        | Домен, реальные SQLite-транзакции, миграции, деньги, дедупликация, атрибуция и наблюдения                         |
| `pnpm test:integration` | HTTP injection, настоящий worker, файловое хранилище, отдельный CLI-процесс, контракты и жизненный цикл адаптеров |
| `pnpm test:e2e`         | Production UI в настоящем Chromium, локальный HTTP, worker и SQLite                                               |
| `pnpm test:coverage`    | Собрать программу, выполнить все группы тестов, объединить покрытие Node/worker/CLI и браузера, применить порог   |
| `pnpm check`            | Strict TypeScript/проверка Svelte, production build и все тесты с порогом покрытия                                |

Test runner ограничен двумя одновременно исполняемыми файлами: Chromium, native worker и coverage writing не должны конкурировать без ограничения за CPU/диск CI. Таймауты пользовательских операций и проверки результатов при этом сохраняются.

`pnpm test` сохранён как быстрый запуск компилируемых core/daemon-тестов. Для готовности изменения нужен `pnpm check`, а не только этот быстрый набор.

## Измерение покрытия

Область — **весь собственный исполняемый код приложения** в `packages/core/src`, `apps/daemon/src`, `apps/web/src`, включая новые файлы и подкаталоги. Node V8/c8 измеряет демон, workers и отдельные процессы. Playwright V8 coverage и source maps измеряют собранный Svelte UI и переводят результат обратно в исходники. Результаты всех навигаций и тестов объединяются; перед переходом/перезагрузкой helpers `goto`/`reload` сохраняют checkpoint. Так уничтожение browser document не теряет уже выполненные сценарии. Checkpoint сохраняет только исходники приложения по source map; vendor coverage не записывается повторно при каждой навигации. Это сокращает дисковую нагрузку, не меняя область покрытия.

Порог: **≥90% строк, ветвлений и функций в совокупности**, дополнительно **≥90% строк каждого файла**. Отсутствующий в отчёте runtime-файл означает падение. Для каждого файла сохраняются все три показателя; отдельные непокрытые защитные ветки остаются видны. Итог записывается в `coverage/coverage-summary.json`, подробные счётчики — в `coverage/coverage-final.json`; серверный LCOV — в `coverage/node/lcov.info`.

Исключения: `.d.ts` и стёртые TypeScript-типы не выполняются; внешний код `node_modules` и сгенерированный bundle/runtime не учитываются как собственные исходники. Сам исходный Svelte/TypeScript при этом включён. CI/workflow, настройки сборки, benchmark и тестовый инструментарий лежат вне области runtime-приложения; поведение самого coverage gate проверено отрицательным тестом. Дополнительных исключений собственного кода и `ignore`-директив нет. Наличие сложной ветки или отсутствие живого аккаунта не исключает адаптер из отчёта.

Покрытие V8 — измерение исполнения, а не доказательство всех комбинаций входов. Тесты проверяют содержательные результаты и отказы; «90%» не означает гарантию безошибочности программы.

## Уровни доказательства

- Core: настоящая SQLite с rollback, reopen, online backup, проверкой integrity/FK и старых схем.
- Локальная интеграция: настоящий HTTP/worker/отдельный процесс; Host/Origin, отсутствие логина, конфликт ревизий, ограничение очереди и восстановление после ошибки сериализации.
- Provider wire: тестовые HTTP- и WebSocket-серверы передают реальные кадры `ws`, пагинацию и пересечение WS/REST. SQL пишет настоящий worker; суммы и дедупликация проверяются в базе.
- Provider lifecycle: управляемые часы и транспорт проверяют ожидание/slow_down/expiry, refresh, 401/429, отсутствие scopes, handoff без новых подписок, неожиданный gap, keepalive, неполный poll, отказ канала DA и отмену позднего OAuth-ответа. Они не подтверждают актуальность живого протокола сервиса.
- E2E: запись/остановка, люди/merge/undo/split/aliases, минутная сетка, фильтры и сессии, backup, ошибки форм, Twitch device code, DA OAuth callback и импорт собственного токена; API-conflict, отказ worker и повторный вход после рестарта с сохранённой историей. External provider заменён fixture; production API не содержит маршрута для тестового наполнения.

Данные и секреты fixture искусственные, папки временные. Процент покрытия не закрывает G1–G7 из [validation.md](validation.md): живой owner OAuth, фактические события и права, целевые ОС, sleep/network, восьмичасовая запись и годовая нагрузка требуют отдельных экспериментов.

## CI

`.github/workflows/ci.yml` запускает Quality gate на push всех веток, всех pull request и вручную. Linux server runtime проверяется тремя независимыми сегментами `unit`, `integration`, `e2e`; `fail-fast: false`. Отдельная задача проверяет deployment receiver и shell syntax. Каждый сегмент выполняет production build и сохраняет Node/browser coverage, E2E устанавливает Chromium, unit включает Svelte diagnostics.

`node scripts/test-with-coverage.mjs SEGMENT` запускает сегмент с покрытием. Combined quality gate зависит от успеха всех сегментов и operations, объединяет artifacts и применяет общий порог ≥90% строк/ветвлений/функций плюс ≥90% строк каждого runtime-файла. Проценты отдельных групп не подменяют объединённый результат. Собственные `.test.ts` относятся к тестовому инструментарию, а не runtime. Локальный `pnpm check` выполняет те же сценарии вместе.

Старые ветки до включения workflow используют прежний CI. Обязательный статус при merge дополнительно требует branch protection/ruleset владельца репозитория. Deploy server принимает только полностью успешный Quality gate текущего main.

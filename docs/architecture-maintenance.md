# Архитектура: состояние и порядок рефакторинга

Код следует SOLID и KISS частично. Это оценка конкретных границ модулей, а не сертификат соответствия всем принципам.

## Существующие границы

- `StreamStore` — фасад операций с данными. Его публичный API сохраняется при выделении внутренних модулей.
- `openProfileDatabase` — адаптер: изолирует таблицы и версии профилей за API SQLite.
- `DonationLedger` — отдельный модуль учёта донатов, исправлений и аудита.
- `ProviderStorage` — хранение неразобранных донатов и проверка известных ID.
- `ReadCache` — кэш производных чтений с объединением одновременных запросов; SQLite остаётся источником истины.
- Модули аналитики, присутствия и метрик содержат отдельные расчёты.

## Первый этап

- `database-migrations.ts` отвечает за настройку SQLite и последовательные атомарные миграции. Специальные преобразования версий 3 и 16 выполняются в той же транзакции, что и SQL миграции.
- `PersonAnnotations` отвечает за заметки, теги и ручной признак ядра. Сохранены происхождение данных после объединения людей, проверки ревизий и транзакции.
- Оба модуля получают уже открытое профильное соединение. Новых подключений, контейнера зависимостей или универсального ORM нет.

## Разделение предметных областей

- `StreamSessions` отвечает за жизненный цикл общих стримов, связи площадок и назначение событий. Закрытие последней площадки и связанные изменения выполняются в прежних транзакциях.
- `IdentityLinks` отвечает за идентичности, обратимые объединения/разделения и исправление исторических дублей донатеров. Проверка ревизии передаётся как узкая зависимость; модуль не зависит от фасада.
- `EventIngestion` отвечает за проверку и атомарную запись событий, дедупликацию и модерацию. Получает только нужные операции связей и стримов, без зависимости от всего фасада.
- `AudienceQueries` — модель чтения аудитории и истории. Запросы не меняют факты, не управляют сборщиками и используют существующие расчёты присутствия.
- `store-contract.ts` задаёт единственный список worker-операций и политику кэширования. Аргументы клиентских вызовов выводятся из сигнатур фасада; неизвестные команды отклоняются и во время исполнения.
- Все модули используют одно профильное соединение. Нет взаимной зависимости сервисов от `StreamStore`, дополнительных копий данных или новых уровней транзакций.

## Правила дальнейшей поддержки

1. Новую бизнес-логику добавлять в соответствующий модуль, а в фасаде оставлять делегирование.
2. При изменении схемы использовать единый реестр миграций и сохранять тесты профильной изоляции.
3. Worker-операцию объявлять в одном контракте с явной политикой чтения/записи; не расширять список ради обхода ошибки типов.
4. Оптимизировать запросы после измерений на репрезентативной копии БД. Разделение модулей само по себе не доказывает ускорения.
5. Крупные запросы статистики и обработчик входящих событий можно делить дальше при добавлении соответствующих функций, без создания универсального фреймворка.

Рефакторинг сохраняет поведение и проверяется профильными, миграционными и интеграционными тестами. Паттерны добавляются только для решения конкретной проблемы. Количество классов и строк само по себе не служит мерой качества.

Cached reads live for at most 30 seconds in local memory and Redis, and domain mutations invalidate both immediately. Concurrent identical requests share one calculation. Live analytics and rolling People windows use a 30-second cache key interval while retaining the original query timestamps; historical filters remain exact. Heartbeats, quota accounting, import retry bookkeeping, backup reads and derived-cache warming do not discard domain reports. Start/stop lifecycle and domain writes still invalidate reports. Memory/entry/response size limits and outage fallback remain enforced.

## Обновление открытого экрана

`ui_revisions` хранит пять счётчиков фактических изменений отдельно для каждого профиля. SQLite-триггеры учитывают записи и исправления фактов; одинаковый payload, курсор сборщика и запись производного кэша счётчики не меняют. Worker сбрасывает кэш чтений после реального изменения, включая изменения с другого клиента того же профиля. Проверка версий также сбрасывает старые ответы после исправления фактов через отдельное подключение к базе.

Клиент проверяет `/api/v1/changes` для открытого профиля: по умолчанию раз в пять минут без эфира и раз в минуту в живом контексте. Скрытая вкладка не опрашивает сервер. Проверка версий не загружает отчёт; неизменившиеся исторические снимки сохраняются при навигации. Изменения донатов, людей и настроек учитываются и без эфира. Счётчики подписчиков обновляют свой график отдельно. Расписание сборщиков провайдеров сохранено.

Аналитика запрашивается только при открытии аналитики или конкретного стрима. Параметр `panel` сокращает ответ до текущего подраздела без изменения расчётов. Предварительная обработка сохранена для просматриваемого профиля: короткая аренда интереса браузера ограничивает фоновую работу, а завершённая версия повторно не обрабатывается. Возвращаемость использует `attendanceOnly=1`; записи доноров без участия в эфире остаются в общих данных и донатах, но не увеличивают число участников.

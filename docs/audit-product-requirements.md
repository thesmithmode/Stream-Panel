## Обязательная новая приёмка перед внешним доступом

1. Закрытый HTTPS URL доступен с внешнего ПК и телефона без SSH/тоннелей; гостю недоступны данные и mutations. На проверенном main сейчас открытый API (`hosted.ts:45`, `:60`, `:81`), и тест прямо ожидает `persons=200` без входа (`hosted.test.ts:15`): это блокирует публикацию.
2. По последнему уточнению пользователя оба авторизованных аккаунта могут выбирать оба профиля. Профили сохраняют отдельные данные и настройки; запросы одного клиента не переключают область другого. Гостям недоступны данные, изменения и общие резервные копии. Предыдущее ограничение Гульназ только своим профилем отменено пользователем.
3. Bootstrap, аккаунты, proxy/TLS, Supabase настройки и обновление выполняются только workflow GitHub Actions из main; ручные команды установки из `docs/ops/server.md:14` необходимо заменить CICD. Текущий deploy workflow уже проверяет SHA текущего main и зелёный CI (`.github/workflows/deploy.yml:27`), но bootstrap в нём отсутствует.
4. Изменения и проверки идут через dev/side; production и stable/latest релизы только main. Наличие release/deploy workflow не означает выполненный релиз/деплой. Требуются run URL, terminal success, release SHA на `/healthz`, проверка рестарта и rollback.
5. Локальный шифрованный backup плюс закрытый Supabase Storage должны реально работать; ошибка облака сохраняет возможность получить локальную копию. Отдельно проверить ротацию, восстановление и безопасную выдачу файла владельцу.

Почему такое решение, даже если кажется странным: бесплатный hostname на IP может удовлетворить «без домена» и HTTPS, но безопасность даёт проверенная серверная авторизация, а не сложное имя URL, CORS/Origin или скрытый переключатель. Последнее разрешение пользователя предоставляет обоим аккаунтам оба профиля; вход нужно проверять в backend на каждом пути доступа, включая backups.

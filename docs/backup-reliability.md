# Backup reliability and recovery

Scheduled snapshots are independent of platform collectors. A one-minute scheduler checks persisted last success and creates a verified encrypted SQLite snapshot every 24 hours. Moscow calendar days determine retention: newest snapshot for each of today and the previous six days, then newest available points in days 7–13, 14–20 and 21–29. Seven latest local recovery points are always kept in addition to calendar points. Optional older points have a 2 GiB budget; the seven latest have priority. Pending upload flags do not pin superseded snapshots forever. When cloud is disabled there is no upload queue. Sparse history is never fabricated. Future-dated copies are preserved until the clock catches up.

Each installation has a persisted random identifier under `stream-panel/<installationId>` in the private Storage bucket. Restoring an archive to a new directory creates a new identifier; local machines cannot rotate server archives. Existing unscoped remote archives remain untouched.

Pending uploads survive restart in atomic `backup-state.json`. Startup also recovers published archives whose queue registration was interrupted by a crash. Failed uploads retry after 1, 2, 4, 8, 16, 32, then 60 minutes, capped at one hour. Each scheduler tick uploads up to four oldest pending archives. Immutable duplicate uploads must pass a download/hash comparison. Superseded pending copies follow the same retention budget while seven latest recovery points are preserved. During a long outage, snapshot creation checks free space and fails visibly before exhausting the disk. Cloud errors and outstanding uploads are visible in the authenticated panel and Integrations.

Deployment forwards `STREAM_PANEL_SUPABASE_KEY` from the production GitHub environment to a root-owned, service-readable file. Missing credentials preserve existing settings but the final real cloud restore check fails. The AES recovery key is not rotated by this setup. Two fixed profiles, ruslan and gulnaz, remain supported as requested.

## Recovery procedure

GitHub Secrets cannot be read back through the settings/API. A trusted explicitly dispatched workflow can use the secret. `recovery-proof.yml` compares the GitHub AES key to the actual server key, restores a real local archive into a new temporary directory, checks SQLite integrity/foreign keys/profile schemas, and verifies the Gulnaz password against the live scrypt hash. Only then does it encrypt the requested values to the recipient public key. Neither plaintext credentials nor the private recipient key belong in git or workflow logs. The encrypted export expires after one day. If the recipient private key is lost, generate a new recipient pair before dispatch; this does not change the database recovery key.

Keep the verified AES key in a separate password manager and an independent emergency recovery method. GitHub Secrets alone do not provide an operator-readable recovery copy. A failed credential comparison must not silently reset a user password or rotate the AES key.

- Dispatch the recovery proof on main and decrypt its verified export before handing the AES key and existing Gulnaz credentials to the owner. Dispatch was blocked by automatic approval review's usage limit; do not bypass that rejection with a different execution path.
- After successful export, remove the one-time recovery workflow, script and public recipient key.
- Confirm production is running the new commit, database integrity, Redis invalidation, RAM/disk headroom, pending queue and cloud freshness after deployment.
- Supabase Free may pause inactive projects. Regular uploads do not guarantee exemption. Paid-plan changes require the owner's choice; preserve local pending archives and visible alerts while paused.

Earlier login polling and responsive analytics fixes, Redis cache verification, and main/dev alignment are already in the repository. They must remain covered by the quality gate; do not report a local change as deployed until the server verification completes.


Storage hygiene: startup removes only known interrupted backup staging files and state temporaries. WAL autocheckpoints every 1000 pages and retains at most 64 MiB after a successful checkpoint. A long-lived SQLite reader can temporarily delay this checkpoint; the limit is not a hard bound during a busy reader. Successful diagnostic API responses and chat text are not retained. Normalized events, message-counting metadata, minute samples and minimal follower history remain. Unparsed donations are kept in a deduplicated retry inbox; migration salvages missing donations before removing obsolete raw pages. Startup compacts migrated databases once when sufficient working space is available. Below 1 GiB free, collector writes trigger local backup cleanup and continue; cleanup failure alone does not stop collection. Only the critical 16 MiB floor rejects writes. Backup preflight reserves the actual snapshot/verification working space plus that floor.

Full factual history is intentionally unbounded: a finite disk can eventually fill with real data. Seven full recovery snapshots require additional storage proportional to database size. No policy can promise infinite history on a finite volume; add storage or a verified archival workflow before factual history reaches capacity. Retention never silently drops chat, donations, people, samples or stream history.

Long-history maintenance (schema 17–18): follower payloads are shared by content hash while every original poll ID/time survives in follower_checks. Compact event indexes retain lookup semantics and public event IDs. Closed-stream analytics use revisioned compressed derived reports; late events, donation edits and membership/name changes invalidate affected streams. Preparation and composition return bounded progress batches; original facts remain available through day/stream drill-down. Large-period curves use duration-weighted local-day means, never a cumulative audience count. Daily message counts remain sums. Each physical SQLite file has one shared worker queue with a 128 MiB V8 old-generation limit and 8 MiB young-generation limit; profile stores, connections, cache keys and IPC replies remain isolated and an unexpected worker exit causes service shutdown so systemd can restart it. Health diagnostics run every six hours on main.

SPBK2 streaming payload/archive limits are 64 GiB; SPBK1 buffered legacy limits remain unchanged. Raising the format guard does not provision disk space: snapshot preflight still checks working space. The hosted entrypoint allocates 1,000,000,000 bytes to this installation's cloud copies by default; STREAM_PANEL_CLOUD_BACKUP_BUDGET_BYTES can set an explicit allocation. The upload reserves space before sending any object, counts owned files/manifests/parts and fails visibly when the allocation is insufficient or size metadata is unavailable. It never deletes verified recovery points to make an upload fit. This is an installation budget, not a live measurement of the organization's subscription quota or other projects/buckets. Future growth can require more disk or an explicitly selected storage plan; no paid upgrade is automatic.

Synthetic capacity check: 7,305 one-hour broadcasts × 500 chat metadata events = 3,652,500 events with 100 recurring identities. Compact indexes reduce this fixture from about 4.63 GB to 3.55 GB before derived reports; populated report caches bring it to about 3.66 GB. The latest 100 streams read in 66 ms and 100 people in 346 ms on the test host. Two independent store clients concurrently composing the same complete fixture through the shared queue peaked at 342,802,432 bytes RSS for the test process; repeated reports took 446 ms for both responses. These measurements exclude the separate frontend process, presence memberships, follower history, backups and provider/network failures. They are a reproducible workload observation, not a ten-year availability or fixed-capacity guarantee.

Downloading an existing snapshot streams the immutable encrypted file with Content-Length; it creates no archive or staging file. Manual creation responds after local verification instead of waiting for cloud upload; cloud state and retries remain visible independently. Scheduled and pre-restore snapshots continue to wait for their existing completion path.

Daily reliability follow-up (2026-10-15): the freshness deadline is now the 24-hour interval plus two hours for scheduled retries/uploads, shared by deployment verification and read-only server health. Restore verification remains in the deployment workflow; no additional weekly restore job was introduced. Before checking the cloud allocation, rotation may remove only points already superseded/expired under the policy computed from existing published copies, always preserving the newest existing point (even after a long offline interval) and an idempotent upload target. A new, unverified upload cannot displace a protected recovery point. If the retained points plus the new upload do not fit, the upload fails visibly and local data/copies remain intact. Unpublished chunk directories are still conservatively counted; automatic orphan deletion is deferred until a safe lease/age policy is implemented.

Snapshots above 1 MiB use the existing streaming SPBK2 writer and local verification; tiny snapshots and legacy restores remain compatible. The synthetic `node scripts/benchmark-backup.mjs [baseline-module]` fixture creates and restores a disposable 24 MiB database. On this host the prior buffered implementation peaked at 230,735,872 bytes RSS versus 111,845,376 bytes after the change (982 ms versus 1,648 ms creation). This is a process-local measurement, excluding collectors, frontend, Redis and cloud transfer; it does not prove the cause of historical server OOM events.

Closed-stream reports remain reusable while their fact/settings revisions match, including streams older than 48 hours. Late donations and identity changes still invalidate derived results. Compressed report payloads have a total 128 MiB budget per profile, with deterministic oldest-write eviction and 16 variants per stream. Background warming never evicts an otherwise useful cache entry just to cycle through oversized history; on-demand composition progresses in bounded slices even when all historical reports cannot fit simultaneously. Eviction affects derived data only; SQLite may reuse freed pages instead of immediately shrinking the physical file.

The person event feed narrows candidates through existing identity/event indexes before applying effective donation attribution. API limits and filters are unchanged. `node scripts/benchmark-person-feed.mjs [baseline-module]` reproduces the synthetic 480,000-event comparison and prints query plans. A repeated run measured a 233.1 ms baseline median versus 3.3 ms after the change, with identical results. This is not a network latency or future production guarantee.
